## 6. 缓存与重算规则（最容易踩坑）

各阶段结束后写 receipt，重跑时比对签名，一致则直接复用。

会命中缓存：关掉应用再开、重开同一视频、只改视图设置、模型之间来回切换查看。

会导致重算：

| 改动 | 影响范围 |
| --- | --- |
| 相机模式 / 平滑 / FlowHMR 采样间隔 | 该模型推理阶段 |
| 裁剪范围、替换源视频 | 全部阶段 |
| 替换模型权重文件 | 用到该权重的阶段 |
| Resource Mode（Automatic ↔ Low Memory） | GVHMR 全量重算 |

GVHMR 的缓存签名（mocap/gvhmr_preprocess.py:20）包含运行时算出的 batch、core_frames、threads、GPU 名称等：

- Automatic（显存预算 ≥3.5 GiB）→ image_batch=16、core_frames=1024
- Low Memory → image_batch≤4、core_frames=256

所以同一视频、UI 参数不变，只要资源模式变了，GVHMR 就会整条链重跑。ExMR 的签名不含 batch，不受此影响。

建议：调脚部/地面/锁定强度只走 Apply Correction（秒级）；确需切换资源模式时接受一次重算。

## 8. BVH → BIP 交付说明

脚本：`F:\Comfy-Desktop\ComfyUI-Installs\Comfy-MotionCapture\bvh_to_bip.ms`
调用：`3dsmax.exe -q -silent -mip -U MAXScript bvh_to_bip.ms`，读取同目录 bvh_to_bip_params.txt（6 行：bvh 路径 / bip 路径 / fps / spineLinks / elbowOrient / jointsOut），结果写 bvh_to_bip_result.txt，单次超时 300 秒；参数文件全局共享，必须串行执行。

本次参数：fps=30、spineLinks=4、elbowOrient=1。

> 应用内也可用 `copy_bvh` + `bvh_profile=biped` 直接生成 Biped 兼容 BVH（见第 14 节）；它不替代 `bvh_to_bip.ms`，后者仍负责 BVH→BIP。

交付物（`H:\MyProject\Video2Motion\视频转动作小强确认20261103`）：

| 目录 | 内容 |
| --- | --- |
| 视频1_lastyearsummer | lastyearsummer_{exmr,gvhmr,flowhmr}_ta.bip + 原 motion.bip / motion_real.bip |
| 视频2_mandance | mandance_{exmr,gvhmr,flowhmr}_ta.bip + 原两个 bip |
| 视频3_womandance | womandance_{exmr,gvhmr,flowhmr}_ta.bip + 原两个 bip |

命名规则：<视频>_<模型>_ta.bip，ta 表示已做手臂 T-pose→A-pose 变换的版本。

T→A 变换内容（与管线 clean_bvh_autodesk.py 一致）：

- LeftElbow / RightElbow / LeftWrist / RightWrist 的 OFFSET：(±x,0,0) → (0,-|x|,0)，长度不变；
- 每帧对 Shoulder 右乘 Mᵀ，对 Elbow/Wrist 做共轭 M·R·Mᵀ（M = Rz(∓90°)），再按 ZXY 分解回欧拉角；
- 其余 45 个关节数值零改动。

验证结论：

| 指标 | 结果 |
| --- | --- |
| 帧数 | 229 / 498 / 658，与源 BVH 完全一致 |
| 骨架 | 36 节点，四段脊柱（spineLinks=4 生效） |
| 手骨与前臂夹角 | 原版 84–91°（垂直，即已知 bug）→ TA 版 148–167°（顺着手臂） |
| 关节世界坐标 | Pelvis / Hand / Foot / Head 与未变换版差异 0.0 mm（姿态未被改动） |
| 指骨末端 | 恒定偏移 138.7 mm（手部朝向被旋正的结果，非抖动） |
| 文件差异 | TA 版与未变换版 bip 有 66% 字节不同，改动确实写入文件 |

## 13. Motion Correction 屈膝问题分析（2026-11-04 追加）

### 13.1 现象与结论

woman_dance 360 帧，原视频腿部是直的；勾选 **Enable Correction + Foot + Flat Ground** 后，导出动作明显屈膝；取消 Foot 后问题消失。

结论：不是导出/重定向 bug，是 `correct` 阶段把两只脚都锁到同一水平面，骨盆被多降，固定骨长下膝盖只能弯曲吸收。取消 Foot 时 `contact_ranges=[[],[]]`，active 全为 False，整条修正链为空操作，所以看不到。

当前 woman_dance 工程状态（2026-11-04）：

| 模型 | 当前结果 | mode | Foot |
| --- | --- | --- | --- |
| ExMR | `corrected_initial` | `multi_level`（10:45 重跑） | 开 |
| FlowHMR | `corrected_initial` | `flat` | 开 |
| GVHMR | `corrected_footmr_refined` | `flat` | 开 |

### 13.2 360 帧数据（Flat Ground + Foot，normal）

| 模型 | 源左/右膝 | 修正左/右膝 | 骨盆 Y 变化 |
| --- | --- | --- | --- |
| ExMR | 9.7° / 7.1° | 33.6° / 5.2° | -3.17 cm |
| FlowHMR | 11.6° / 9.3° | 20.1° / 14.3° | -5.98 cm |
| GVHMR | 15.5° / 8.4° | 27.9° / 36.9° | -6.96 cm |

SMPL-X 静息膝角：左 13.2°、右 8.4°；源动作基本就是直腿。

GVHMR 的根节点分解：

- -6.96 cm = 接地 -2.29 cm + reach 补偿 -2.88 cm + 时间规划 -1.78 cm
- 左踝 -5.26 cm、右踝 -2.45 cm；左/右髋-踝距离缩短 1.68 / 3.96 cm → 膝 +12.4° / +28.5°
- floor = 0.0707；左/右鞋底最低 0.1233 / 0.0951；右踝-鞋底 0.170 m，左 0.079 m；两脚都 active，右前脚掌概率 0.662。

两只脚脚型不同（右脚更绷脚背）→ 同一平面约束无解；根跟着较低鞋底接地，较高鞋底把骨盆继续往下拉，另一条腿被压弯。

### 13.3 脚后跟落地能否消除屈膝

不能单独解决。

- ExMR 360 帧屈膝 33.6° 的是平脚（脚跟仅高 0.94 cm）；FlowHMR 20.1° 的左脚几乎全脚掌着地；当前 GVHMR `corrected_footmr_refined` 屈 36.0° 的左脚脚跟仅高 0.15 cm。
- 当前修正只改踝位置、不改踝旋转（`max_ankle_global_change_deg ≈ 7e-6`）；三个 preset 都写明 “inferred foot rotation is retained”。脚后跟抬起是从源 HMR 姿态继承的，不是修正阶段新加的。
- 强行压平脚后跟会把踝降低约 9 cm，腿更伸展；为让脚仍贴地，骨盆需再下降约 4–5 cm，另一条腿会弯得更多。是“转移弯曲”，不是“消除”。
- 如果视频确实是全脚掌着地，应修正源脚部旋转/接触，或手动调整接触；不是 Flat/Multi 或 preset 能单独修的。

### 13.4 Flat Ground vs Multi Level（ExMR 360 帧）

| 量 | 源 | Flat | Multi |
| --- | ---: | ---: | ---: |
| 骨盆 Y | 1.0232 | 0.9915 | 1.0220 |
| 左膝 | 9.7° | 33.6° | 10.3° |
| 右膝 | 7.1° | 5.2° | 11.9° |
| 左脚支撑 Y | 0.0466 | 0.0471 | 0.0462 |
| 右脚支撑 Y | 0.0774 | 0.0468 | 0.0793 |
| 右脚 heel-fore | +3.53 cm | +3.55 cm | +3.45 cm |

整段 658 帧：

| 指标 | Flat | Multi |
| --- | ---: | ---: |
| 相对源动作的附加膝角均值（左/右） | 7.28° / 6.17° | 2.42° / 3.29° |
| 附加膝角 p95 | 22.75° / 21.52° | 10.37° / 11.52° |
| 附加膝角 >10° 的帧数 | 216 / 139 | 34 / 48 |
| 根节点相对源偏移 p95 / 最大 | 30.6 / 32.4 cm | 3.2 / 5.8 cm |
| 左右脚支撑高度差均值 | 1.97 cm | 4.65 cm（源 4.66） |

- Multi 保住了左腿，但右脚仍比左脚高 3.3 cm、脚跟仍抬 3.45 cm；它是“保腿型、放弃单地面”。
- 平地场景仍优先 Flat Ground；Multi 仅在 Flat 明显破坏腿型、且能接受脚悬空时作为工作流折中。不能宣称 Multi 修复了脚部。
- 要两者都对，需要改源脚部姿态/接触，或手动调整接触；仅切模式做不到。

### 13.5 Lock Preset 参数与实测

| 参数 | weak | normal | strong |
| --- | ---: | ---: | ---: |
| `confidence` | 0.75 | 0.65 | 0.65 |
| `release` | 0.75 | 0.65 | 0.50 |
| `minimum` | 0.06 | 0.06 | 0.06 |
| `anchor_drift` | 0.12 | 0.12 | 0.20 |
| `strength` | 0.6 | 1.0 | 1.0 |
| `gap` | 0 | 0 | 0.08 |
| `ramp` | 0.16 | 0.10 | 0.06（当前代码未读取） |

- weak：进入接触最严、释放最容易、位置修正只施加 60%；保留更多源动作，脚可能滑/浮。
- normal：默认；稳定接触全量位置保持，自动换步平滑。
- strong：保留更低置信度接触、桥接短暂离地、允许更大 anchor 漂移；可能过度锁定。
- 360 帧实测：weak 29.0° / 34.0°，normal 27.9° / 36.9°，strong 28.2° / 36.7°；weak 只减轻/重分配，不消除。
- 三个 preset 都不改脚踝旋转，不能把脚后跟压平。
- `ramp` 只在 `correction_settings.py` 定义，`correction.py` 没有读取；过渡长度由 `contact_offsets` 自适应计算。

### 13.6 建议

- 平地 + 脚贴地优先 → Flat Ground；若 360 帧屈膝不可接受 → 先检查两脚支撑高度差/脚型差，再考虑 Multi。
- 交付前逐帧目检 360 附近：脚是否悬空、脚跟是否抬起；不要只看膝盖。
- 需要“脚贴地 + 腿直”同时成立时，改源脚部旋转/接触，或接受其中一项折中。

## 14. Worker API：Reconstruct 3D 与 Biped BVH

### 14.1 没有 HTTP API

GUI 的 Reconstruct 3D 是 `prepare` + 模型 stage + `correct` + `export/flow_export` 的 worker 子进程序列。`docs/AGENT_GUIDE.md` 明确 GUI 是受支持界面，不假设通用 CLI API；下面是内部接口，升级可能变。

入口：`mocap.paths.worker_command(stage, *args)`；安装版设置 `RGB_MOCAP_MANAGED=1`；每个 stage 用 `worker_boot.py` 选择对应 runtime。

### 14.2 stage 序列

| 模型 | 含修正的 stage 序列 | result |
| --- | --- | --- |
| ExMR | `track → exmr_preprocess → exmr_features → exmr → correct → export` | `corrected_initial` |
| FlowHMR | `track → flow_camera → flow_features → flowhmr → correct → flow_export` | `corrected_initial` |
| GVHMR（最小） | `track → gvhmr → correct → export` | `corrected_initial` |
| GVHMR + HTD | `track → gvhmr → pva → refine → correct → export` | `corrected_refined` |
| GVHMR + FootMR | 在 `correct` 前加 `footmr` | `corrected_footmr_refined`（或 `_initial`） |
| GVHMR + HandFlow | 在 `correct` 前加 `handflow` | `corrected_handflow_*` |

`prepare` 参数：

```text
prepare --video <mp4> --start <秒> --end <秒> --motion-tool <exmr|flowhmr|gvhmr> --result <result>
        [--correction-mode flat|multi_level] [--correction-preset weak|normal|strong]
        [--foot-lock 1|0] [--hand-lock 1|0] [--pelvis-offset <米>] [--floor <米>]
```

`prepare` 写 `project.json`；后续 stage 用 `--project <prepared project> --result <result>`。

模型参数：

- ExMR：`RGB_MOCAP_EXMR_OPTIONS='{"static_camera":true,"smoothing":"global"}'`
- FlowHMR：`RGB_MOCAP_FLOW_INTERVAL`、`RGB_MOCAP_FLOW_FAST_SAM`、`RGB_MOCAP_FLOW_BATCH4`、`RGB_MOCAP_FLOW_GPU_CROP`
- 资源模式：`RGB_MOCAP_COMPUTE_MODE=auto|low_memory`

只改修正参数不必重跑推理：重跑 `prepare` + `correct` + `export`，推理 stage 会命中缓存。

### 14.3 Biped BVH 导出（copy_bvh）

`copy_bvh` 是 BVH 导出 stage，不是 Reconstruct 3D 的一部分。request JSON 每行：

```json
{
  "project": "<model_project>",
  "kind": "corrected_initial",
  "source": "<selected_export 返回的 52 骨骼目标 BVH>",
  "target": "<输出 .bvh>",
  "bvh_profile": "biped",
  "prepend_tpose": false
}
```

- `bvh_profile="biped"`：Character Studio 命名 + 统一 ZXY；保留 52 关节、手指、offset、米制、Y-up。
- `source` 必须是 `mocap.motion_tools.selected_export(project, kind)` 返回的目标 BVH，不是 22 骨骼的 `*_motion.bvh`。
- 已实测 ExMR woman_dance 的 Biped 导出：`copy_bvh` 返回 0，输出约 1.36 MB，`ROOT Hips`、`LeftHip/LeftKnee/LeftAnkle`、ZXY。
- 它 **不调用 3ds Max/Biped**，只写兼容 BVH；仍需在 3ds Max 里 Motion Capture 载入。文档说明 3ds Max 本身未验证。
- 原有 `bvh_to_bip.ms`（BVH→BIP）仍需在 3ds Max 里跑；`copy_bvh` 只是生成 Biped 可读的 BVH 前置步骤。

注意：模型文件必须先装好；需要 GPU/CUDA；不要并发跑同一 project；`--force` 强制重算；`rig` 生成最终 Mixamo/Humanoid52 `motion.bvh`，`export`/`flow_export` 不是最终角色 BVH。

## 15. 运行时、模型与磁盘占用

- `runtime*` 是 Python 环境/overlay，`models` 是权重；两者不重复。runtime 里没有 >20 MB 的 ckpt/pth/safetensors。
- 真实占用（一次 du，硬链接只算一次）：models 29G、runtime 5.4G、runtime_exmr 5.2G、.setup 11G、projects 1.2G、runtime_character 894M、runtime_flow 603M、runtime_gui 484M、tools 283M；总计约 50–55G。
- `third_party` 表观 95.3 GiB（52 个 >100 MB 文件），但其中 checkpoint 是 `models` 的硬链接：例如 Sapiens 6.08G 有 5 个链接（models、cache/exmr、FootMR、GVHMR、HTD-Refine），实际只占 6.08G；`third_party` 独有代码约 39M。磁盘分析工具会把硬链接重复计算，不要按 100G 删。
- `cache/exmr` 单独看 12G，也是硬链接；删掉不释放多少空间，ExMR 启动时会重建。
- 真实重复/可清理：
  - `mano_v1_2.zip` 168M（MANO 已导入后可删）
  - `models/body_models/smplx/.mesh-lbs-v1-*.npz` 66M（派生缓存）
  - `.setup/downloads` 7G（安装 wheel 缓存；装好可删，修复/更新会重新下载）
  - `.setup/pear-downloads` 129M（不用 PEAR 可删）
  - `docs` 31M（含本交接文档 `交接文档_环境与交付.md`）、`debug.log`、`developer-build` 可选
- 不要手工删 `third_party/*/inputs/checkpoints`、`third_party/FlowHMR/ckpts`、`cache/exmr`；删了表观大小降，真实空间不释放，且上游路径会缺文件。
- 备份/打包注意：普通 ZIP/复制会展开硬链接，50G 可能变成 100G+；用保留硬链接的工具，或按第 16 节排除硬链接目录。

## 16. 离线部署到另一台机器

### 16.1 目标机要求

- Windows x64、NVIDIA 驱动支持 CUDA 12.x、NTFS、至少 70–80G 空闲。
- 应用和 `models` 放同一 NTFS 盘（`os.link` 需要同卷；跨卷 symlink 可能需管理员）。

### 16.2 复制什么

**必须带**：

- 代码/入口：`mocap`、`app.py`、`launch_source.py`、`worker_boot.py`、`scene_boot.py`、`mamma_worker_boot.py`、`prompthmr_worker_boot.py`、`RGBMoCap.cmd`、`install.cmd`、`update.cmd`、`Setup_*.cmd`、`installer`、`prebuilt`、`tools`、`assets`、`native_compat`、`requirements*`、`pyproject.toml`、`SETUP_RECEIPT.json`、`SOURCE_MANIFEST.json`。
- `runtime*`：`runtime`、`runtime_gui`、`runtime_flow`、`runtime_hand`、`runtime_htd`、`runtime_exmr`；角色导出加 `runtime_character`；PEAR 加 `runtime_pear`。
- `models`：整个目录（含 `*.receipt.json`）；按需可只带用到的子目录。
- `.setup`：`bootstrap-git`（uv + Blender/ffmpeg zips）、`python`、`downloads`（7G，保证不重新下载 wheel）、`pear-downloads`（可选）、`git-runtime-state.json`、`pear-*.json`。
- `third_party`：代码和小的外部资产；**排除** `*/inputs/checkpoints`、`FlowHMR/ckpts`、`FlowHMR/checkpoints`、`FlowHMR/assets/body_models/smplh`。
- 排除：`cache/exmr`、`models/body_models/smplx/.mesh-lbs-v1-*.npz`、`mano_v1_2.zip`、`.setup/git-support-*`、`.setup/logs`、`.setup/staging`、`.setup/tmp`。
- 可选：`projects`/`outputs`（旧项目）、`docs`、`.git`。

### 16.3 拷贝方式（不压缩优先）

- 不要压缩整个工程；模型已压缩，ZIP 不会明显变小，且可能改 mtime。
- **SMB + robocopy（推荐）**：

```bat
robocopy "H:\MyProject\toyxyz_RGBMocap" "\\TARGET\RGBMocap" /E /COPY:DAT /DCOPY:DAT /R:2 /W:2 /MT:8
```

  加上第 16.2 节的 `/XD` 排除项。`/COPY:DAT` 保留时间；直接复制约 50G，不展开硬链接（因为已排除）。

- **RDP 磁盘映射**：`mstsc` → Local Resources → Drives 勾选源盘；在目标机用 `robocopy "\\tsclient\X\...\toyxyz_RGBMocap" "D:\RGBMocap" ...`。
- **SSH/SCP**：先本地 staging，`scp -rp`；Windows OpenSSH 对 100ns mtime 保留不完美，复制后检查/修 receipt。
- **只能文件中转**：做 VHDX（NTFS 虚拟盘），把 staging 放进去，传 VHDX，目标机挂载后 robocopy 出来；比 ZIP 更可靠。

### 16.4 关键：models 的 mtime

`models/*.receipt.json` 记录 `[size, mtime_ns]`；mtime 变了会判 Missing。必须用 `/COPY:DAT` 保留时间。若已变，按新 `stat` 更新回执（保留 sha256），或用 Model Manager 重新 Import。

### 16.5 目标机安装与验证

1. 目标机运行 `install.cmd`；
2. 看到 `Keeping verified ... runtime`、`Using verified download` 表示复用；
3. 如果仍然联网，检查 `.setup/downloads`、`.setup/bootstrap-git`、`SETUP_RECEIPT.json`；
4. 启动 `RGBMoCap.cmd`，Model Manager 全绿；
5. 第一次跑模型会自动重建 `third_party`/`cache` 链接，这是正常现象；
6. 检查 360 帧附近的脚部/膝部，不要只看整体。

## 17. Git 更新与目标机器维护

- Git 只跟踪源码：`.gitignore` 排除 models、runtime*、.setup、projects、cache、third_party checkpoints、tools/bin、*.zip 等；`.git` 约 43M。
- 初始部署若要目标机直接更新，**带上 `.git`**（复制命令里不要排除 `.git`）；目标机安装 Git for Windows。
- 目标机能访问 origin：`update.cmd`（要求 branch `main`、tracked 文件干净；会 `git pull --ff-only` 后跑 install/verify；写 `.setup/git-sync.pending`，失败时启动器拒绝启动）。
- 不能访问 GitHub/VPN：
  - 源机 `git bundle create D:\RGBMocap.bundle --all`，传过去；目标机 `git fetch bundle main` + `git merge --ff-only FETCH_HEAD` + `install.cmd`。
  - 或局域网 bare repo：源机 `git clone --bare ... \\SERVER\share\RGBMocap.git`，目标机 `git remote set-url origin ...`，源机 push，目标机 `update.cmd`。
- 没有 `.git`：只能替换 tracked 文件 + `install.cmd`，不能用 `update.cmd`；可 `git init` + `git fetch` + `git reset --hard` 补仓库（会覆盖 tracked 文件）。
- Git 更新不能更新 models/runtime/.setup；模型单独复制（保留 mtime）；runtime 变化让 `install.cmd` 修复；新依赖需要新 wheel 时，源机先跑一次 install/update，把新的 `.setup/downloads` 同步到目标机，否则目标机需联网。
- 更新前检查 `git status --porcelain --untracked-files=no` 为空、分支 `main`；不要删 `.setup/git-sync.pending`（应修复 install）。
